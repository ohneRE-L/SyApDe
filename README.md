# Служба поддержки и тикет-система (Helpdesk / Service Desk)

Репозиторий содержит материалы лабораторных работ по проектированию архитектуры программного обеспечения, описанию спецификации REST API, построению модульного бэкенда по принципам Clean Architecture, контейнеризации приложения с помощью Docker, а также интеграции с СУБД PostgreSQL, управлению версионируемыми SQL-миграциями и оркестрации через Docker Compose.

## Назначение проекта

Система решает задачи автоматизации сервисного обслуживания:
* Прием, классификация и маршрутизация обращений клиентов.
* Контроль дедлайнов реагирования и решения инцидентов в соответствии с матрицей SLA.
* Ведение единой хронологической ленты диалога с поддержкой файлов-вложений и внутренних служебных заметок.
* Аудит нарушений регламентов обслуживания для аналитики качества сервиса.

## Оркестрация через Docker Compose (Лабораторная работа №5)

В проекте настроена оркестрация трех взаимосвязанных сервисов:
1. **`db`**: СУБД PostgreSQL 16 Alpine с сохранением данных в именованном томе `pgdata` и проверкой `healthcheck` (`pg_isready`).
2. **`migrate`**: Контейнер утилиты миграций `golang-migrate`, запускающийся строго после готовности базы (`condition: service_healthy`), накатывающий схему из `migrations/` и завершающийся с кодом 0.
3. **`app`**: Серверное приложение FastAPI, стартующее только после успешного завершения миграций (`condition: service_completed_successfully`).

### 1. Запуск инфраструктуры проекта
Собрать образы и запустить все сервисы в фоновом режиме:
```bash
docker compose up --build -d
```

Проверка статуса запущенных контейнеров:
```bash
docker compose ps -a
```
*Ожидаемый статус:* `db` — `healthy`, `migrate` — `Exited (0)`, `app` — `Up`.

### 2. Проверка журналов мигратора и приложения
```bash
docker compose logs migrate
docker compose logs -f app
```

### 3. Проверка созданной схемы БД и версии миграций
Подключение через `psql` внутри контейнера базы данных:
```bash
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c "\dt"
```
Проверка таблицы версионирования `schema_migrations`:
```bash
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c "SELECT version, dirty FROM schema_migrations;"
```
*Ожидаемый результат:* `version = 1`, `dirty = f`.

### 4. Проверка эндпоинта состояния здоровья `/health` (Health Check)
При работающей базе данных эндпоинт возвращает HTTP 200:
```bash
curl -i http://localhost:8080/health
```
*Ожидаемый ответ:*
```json
HTTP/1.1 200 OK
content-type: application/json

{"status":"ok","db":"up","app_name":"Helpdesk Service Desk API","version":"1.0.0","environment":"development"}
```

Имитация сбоя СУБД (остановка контейнера базы):
```bash
docker compose stop db
curl -i http://localhost:8080/health
```
*Ожидаемый ответ:*
```json
HTTP/1.1 503 Service Unavailable
content-type: application/json

{"status":"unavailable","db":"down","app_name":"Helpdesk Service Desk API","version":"1.0.0","environment":"development"}
```

Восстановление работы СУБД:
```bash
docker compose start db
curl -i http://localhost:8080/health
```

### 5. Проверка ограничений целостности (CHECK constraints)
Корректная вставка (приоритет HIGH):
```bash
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c \
"INSERT INTO categories (title, description) VALUES ('Сетевые неполадки', 'Проблемы с VPN и DNS');"
```

Попытка вставки с недопустимым значением (проверка CHECK constraint `role`):
```bash
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c \
"INSERT INTO users (name, email, password_hash, role) VALUES ('Hacker', 'hacker@corp.local', 'hash', 'SUPERUSER');"
```
*Запрос завершается ошибкой:* `new row for relation "users" violates check constraint "users_role_check"`.

### 6. Проверка сохранности данных (Persistence)
Пересоздание контейнеров с сохранением тома `pgdata`:
```bash
docker compose down
docker compose up -d
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c "SELECT title FROM categories;"
```
*Запись `Сетевые неполадки` сохраняется.*

### 7. Откат и повторное применение миграций
Откат миграции на 1 шаг назад (`down 1`):
```bash
docker compose run --rm migrate -path=/migrations -database "postgres://helpdesk_user:helpdesk_password@db:5432/helpdesk_db?sslmode=disable" down 1
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c "\dt"
```
*Таблицы системы удалены, остается только `schema_migrations` со статусом `version = 0`.*

Повторный накат миграции (`up`):
```bash
docker compose run --rm migrate -path=/migrations -database "postgres://helpdesk_user:helpdesk_password@db:5432/helpdesk_db?sslmode=disable" up
docker compose exec db psql -U helpdesk_user -d helpdesk_db -c "\dt"
```

## Ответы на контрольные вопросы (Лабораторная работа №5)

**1. Зачем нужны down-миграции? Почему откат миграции, удаляющей столбец или таблицу, не всегда безопасен?**
* **Ответ:** Down-миграции обеспечивают обратимость изменений схемы базы данных. Они необходимы в процессе разработки для локального тестирования миграций, а также в аварийных ситуациях при сбое деплоя новой версии (rollout rollback).
* **Опасность отката:** Если миграция удаляет столбец или таблицу (`DROP COLUMN` / `DROP TABLE`), содержавшиеся в них данные безвозвратно уничтожаются на этапе `up`. Down-миграция восстановит структуру таблицы (`CREATE TABLE`), но не сможет восстановить утраченные пользовательские данные. Поэтому в продакшене деструктивные изменения делают в несколько этапов (deprecation phases).

**2. Почему нельзя изменять уже применённый файл миграции? Как инструмент миграций определяет, какие миграции уже применены к базе данных?**
* **Ответ:** Примененные файлы миграций фиксируют историческое состояние схемы. Если изменить уже примененный файл, нарушится детерминированность: на машинах других разработчиков и на прод-серверах состояние базы разойдется, а контрольные суммы (хеши) мигратора не совпадут. Новые изменения всегда оформляются отдельной новой миграцией с инкрементом номера версии.
* **Механизм определения:** Инструмент миграций создает в целевой БД служебную таблицу (у `golang-migrate` — `schema_migrations`), где сохраняются номер текущей версии (`version`) и флаг успешности/ошибки (`dirty`). При запуске мигратор сравнивает файлы в каталоге с записью в таблице и применяет только те файлы, чей номер строго больше текущего.

**3. Почему в docker-compose.yml недостаточно указать `depends_on: [db]` и требуется `healthcheck`? Почему приложение всё равно должно уметь повторно подключаться к БД?**
* **Ответ:** По умолчанию директива `depends_on` отслеживает лишь факт запуска процесса контейнера на уровне Docker daemon, но СУБД после старта еще несколько секунд инициализирует файловые страницы, подгружает системные каталоги и не принимает входящие TCP-соединения. Директива `healthcheck` с утилитой `pg_isready` гарантирует, что зависимый сервис запустится только тогда, когда PostgreSQL реально готов обрабатывать SQL-запросы.
* **Необходимость повторных попыток (Retry Logic):** Сеть между контейнерами ненадежна. База данных может временно перезагружаться (плановый restart, failover в кластере, кратковременный сетевой сбой). Если приложение не умеет повторять попытки с паузой (Backoff), первый же кратковременный разрыв приведет к падению контейнера `app`.

**4. Какую роль играет именованный том `pgdata:/var/lib/postgresql/data`? Что произойдёт с данными после команды `docker compose down` и после команды `docker compose down -v`?**
* **Ответ:** Именованный том `pgdata` монтирует хранилище файлов PostgreSQL на хостовой файловой системе вне жизненного цикла контейнера.
* При вызове `docker compose down` контейнеры и сети удаляются, но именованный том `pgdata` **остается неизменным**, гарантируя сохранность данных при последующем запуске.
* При вызове `docker compose down -v` (с флагом volumes) удаляются как контейнеры, так и **сам том с файлами БД**, что приводит к полному уничтожению всех накопленных данных (полный сброс окружения).

**5. В чём разница между значениями `DB_HOST=localhost` и `DB_HOST=db` для приложения, запущенного внутри Docker Compose? Какое значение нужно указать при запуске приложения с хост-машины?**
* **Ответ:** Внутри Docker-сети Compose каждый контейнер изолирован и имеет собственный сетевой стек. Для контейнера `app` адрес `localhost` — это его собственный локальный интерфейс (на котором PostgreSQL не слушает). Значение `db` разрешается встроенным DNS-сервером Docker в IP-адрес соседнего контейнера базы данных.
* **При запуске с хост-машины:** Хост-машина обращается к опубликованному порту на своем собственном интерфейсе (`ports: 5432:5432`), поэтому с хоста необходимо указывать `DB_HOST=localhost` (или `127.0.0.1`).

**6. Что такое пул соединений с базой данных? Почему его размер необходимо ограничивать и как он связан с параметром `max_connections` PostgreSQL?**
* **Ответ:** Пул соединений (Connection Pool) — это набор заранее открытых постоянных соединений с базой данных, которые переиспользуются входящими запросами приложения без затрат на дорогостоящее TCP-рукопожатие и аутентификацию при каждом вызове.
* **Необходимость ограничения:** В PostgreSQL каждое подключение обслуживается отдельным системным процессом ОС, потребляющим оперативную память и процессорные ресурсы. Если размер пула не ограничен, при пике трафика тысячи соединений перегрузят СУБД. Суммарный пул всех инстансов приложения (`кол-во_инстансов × DB_MAX_CONNS`) должен быть строго меньше системного лимита `max_connections` PostgreSQL с запасом для фоновых утилит и администраторов.

**7. Почему пароли нельзя хранить в коде и в docker-compose.yml? Как используются файлы `.env` и `.env.example`?**
* **Ответ:** Хардкод паролей в исходном коде или в `docker-compose.yml` приводит к их попаданию в систему контроля версий (Git) и компрометации проекта.
* **Использование файлов:**
  * `.env.example` хранится в Git как открытый шаблон и спецификация необходимых переменных конфигурации без реальных секретов.
  * `.env` создается локально каждым разработчиком/сервером деплоя, содержит реальные учетные данные и **обязательно заносится в `.gitignore`**, исключая утечку паролей.

**8. Почему для столбцов внешних ключей рекомендуется создавать индексы вручную? Как выбрать правило ON DELETE (CASCADE, RESTRICT, SET NULL)?**
* **Ответ по индексам:** В отличие от первичных ключей (`PRIMARY KEY`), PostgreSQL **не создает индексы для внешних ключей (`FOREIGN KEY`) автоматически**. Без индекса любая операция `JOIN` по ключу или проверка ссылочной целостности при удалении записи из родительской таблицы приведет к медленному полному сканированию дочерней таблицы (`Seq Scan`).
* **Выбор правила `ON DELETE`:**
  * **`CASCADE`:** выбирается для подчиненных сущностей, не имеющих самостоятельного смысла без родителя (при удалении тикета удаляются его сообщения `ticket_messages` и вложения `attachments`).
  * **`RESTRICT` (или `NO ACTION`):** запрещает удаление родителя при наличии ссылок, защищая исторические и справочные данные от случайной утери (нельзя удалить категорию или автора, пока на них ссылаются тикеты).
  * **`SET NULL`:** применяется для опциональных связей, когда удаление родителя не должно приводить к гибели дочерней записи (при удалении учетной записи инженера поле `assignee_id` в тикете сбрасывается в `NULL`, и тикет возвращается в общую очередь).
